## Observations

Two systematic families dominate the misses above, plus one narrower one:

1. **Distributor/manufacturer suffix words that Barezpakhsh appends but Landau's registry never
   carries** — «مزدا پخش», «لاهیجان», `MONAVARI`, `AMATA`, `RAYKALTON`, «دیناپارت» in 4 of the 5
   rows above. `token_jaccard`'s denominator (the union of both token sets) grows by one for every
   such word on either side, so an invoice name that tacks on one or two distributor words costs
   the *correct* candidate exactly as many points as it would cost any other candidate — and a
   shorter, less specific registry entry that happens not to need those tokens either can end up
   scoring higher than the true, more specific match (row 1: the correct «…مزدا 1600» loses to the
   generic «…مزدا» once «لاهیجان مزدا پخش» is added to the union). This is inherent to a bag-of-
   words metric measured against free-text invoice names; the practical mitigation is a supplier-
   name/brand stoplist stripped in `search_term` (a possible future amendment), not a threshold
   change.
2. **Registry entries that are pure word-bag permutations of each other** (rows 2 and 4): a
   combined "front X and rear Y" part vs. "rear Y and front X", or "model NAME (spec) BRAND" vs.
   "(spec) BRAND model NAME", share an identical token set, so `token_jaccard` cannot tell them
   apart (row 2 scores a clean 100 against the *wrong* one of the pair). No threshold fixes this —
   it needs order/structure sensitivity or de-duplicating the registry data itself. Note that
   `Matcher::decide` (unlike this calibration binary, which always takes `scored.first()`) now
   sends an exact top-two tie to review rather than guessing, so a clean 100/100 case like row 2
   would not auto-accept in the real app; this measured precision is therefore a slight
   *underestimate* of the app's actual behaviour on tied pairs.
3. **A spelling variant `normalize_text` does not fold** (row 5): «روا» (bare alef) vs. «روآ»
   (alef-madda) are different characters to Persian text but the same car-model word to a human;
   `normalize_text`'s per-character map unifies ي/ك/ة/أ/إ/ؤ but not آ, so the two spellings are
   disjoint tokens to Jaccard, and a wrong candidate that happens to share the invoice's spelling
   can outscore the correctly-spelled true match. Worth adding `'آ' => Some('ا')` to the map if this
   recurs at scale.
